## To do: independent review of the backup and restore code (the user asked to keep this open)

Run it when the user says go (CLAUDE.md: a separate review pass on changes that touch secrets or the database file; launch a reviewer agent only on the user's word). Scope: `internal/store/backup.go` (`Backup`, `Restore`, `PruneBackups`, `writerLeaseHeld`, `rollback`, `copyFile`, `finishCopy`, `verifyBackup`), `cmd/privo/backup.go`, `cmd/privo/backupjob.go`, the wiring and the master-key check in `cmd/privo/serve.go`, and their tests (`internal/store/backup_test.go`, `cmd/privo/backup_test.go`, `cmd/privo/backupjob_test.go`, `test/acceptance/backup_test.go`). Brief for the reviewer: attack it, do not re-read my tests and agree; report findings as R-12 onward in `docs/reviews/`. Questions I could not settle myself:

1. **Race between the check and the swap:** `Restore` checks the writer lease read-only and then renames the new file into place. A gateway that starts between the two (or one whose lease expired during a stall: `LeaseTTL` is the lease lifetime without a heartbeat) would open a file that is replaced under it. Is the window real, and does a lock file or a rename-based protocol close it?
2. **Stale lease:** after a crash the lease row stays until it expires, so a restore right after a crash may be refused for up to the TTL. Acceptable, or should `--force` override a lease older than N seconds?
3. **Ownership and modes:** the image runs as `nonroot` (65532). A restore run as root (`docker run` without `--user`, or a root shell on the host) leaves a root-owned `privo.db` the gateway cannot open. Should `restore` refuse, or copy the owner of the data directory?
4. **Hard links:** the final name is made with `os.Link` from `<name>.partial`. Some filesystems (certain network mounts, FUSE) have no hard links; is there a fallback or only an error? Does a failure leave the partial behind?
5. **Clock:** the scheduled job waits for `newest snapshot time + interval - now`. A snapshot named with a time in the future (clock set back, restored volume from another host) would suppress backups until the clock catches up. The name regexp also trusts file names.
6. **Disk full:** `VACUUM INTO` needs roughly the database size in free space; on a volume shared with the live database, a failing backup or a pile of kept snapshots can starve the gateway itself. Is there a free-space check, a cap, or a log line that an operator would see in time?
7. **What a backup holds:** the acceptance test proves three tokens, one credential and the master key are absent. Does the file hold anything else that should not travel (audit arguments are stored encrypted when enabled; token hashes; wrapped DEKs)? Is `0600` enough, and should `backup --to` refuse a world-readable parent?
8. **Path handling:** `--from` and `--to` follow symlinks; `PruneBackups` deletes by name pattern in a directory the operator names. Can a crafted `--to`/`PRIVO_BACKUP_DIR` make it delete something else? Does a symlinked `backups` directory matter?
9. **Restore across schema versions:** a snapshot from an older schema is accepted and migrated at the next start; one from a newer schema is refused. Is the migration after restore tested, and is an interrupted first start safe?
10. **Audit of failures:** `backup.create` with outcome `error` is written for scheduled failures; a failed CLI backup writes nothing. A restore that fails half-way: what do the logs and audit say?
