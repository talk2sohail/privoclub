# Independent review: F07 upstream OAuth broker (per-person connections to upstream MCP servers)

- Date: 2026-11-03
- Reviewer: independent review agent (did not write the code)
- Reviewed: `main` at `3e933da`; most of F07 arrived in `c7801b0`. Scope: `internal/upstreamauth`, `internal/grants`, `internal/upstream` (`perperson.go`, `upstream.go`), `internal/web/connect.go`, `internal/store/upstream_oauth.go`, migration `00005`, `internal/control/upstream_oauth.go`, the account resolution in `internal/gateway/gateway.go`, `internal/vault`, and the token-issue path in `internal/control/control.go` that feeds it.
- `git status` at start: clean. No source, test or docs/todo.md file was changed; this report is the only write.
- Method: read the code against ADR 0017 and the F07 section of `docs/todo.md`; ran `go test -race ./internal/upstreamauth/... ./internal/grants/... ./internal/upstream/... ./internal/store/... ./internal/web/... ./internal/control/... ./internal/gateway/...` (all pass); traced each claim in the threat note to code. No throwaway probe was needed beyond the existing tests: where a finding says RAN, an existing passing test already demonstrates the behaviour; where it says READ, I argued it from the code and did not execute it.

## Verdict

**Approve with changes.** The OAuth mechanics (discovery, PKCE, state, callback binding, token storage, refresh CAS, origin lock) held up under adversarial reading. The blocking item is R-01: the binding between a gateway token and "which person's upstream account it uses" is a free-text name that any admin or owner can set, so the "never another person's grant" guarantee holds only against members, not against admins. R-02 and R-03 should be fixed before the feature is called done.

Counts: Critical 0, High 1 (R-01), Medium 2 (R-02, R-03), Low 5 (R-04 to R-08), Info 1 (R-09, several small items).

## Findings

### R-01 High: an admin or owner can mint a gateway token for any member's person and call upstream as that member

- Where: `internal/control/control.go:527-530` (`IssueToken`: `person` is taken from the request, and defaults to the token `name`), `:553-580` (`createToken`: `PermManageTokens` is the only check, `req.Person` is passed through); `internal/gateway/gateway.go:394-412` (`session`: `UserByPerson(c.p.Person)` then `PersonSession(..., u.ID)`); `internal/auth/auth.go:122-126` (`Person` comes from the token record).
- What is wrong: the gateway maps a token to an upstream grant by matching the token's `person` string to `users.person`. Nothing ties the token to the user who asked for it. `POST /api/v1/tokens` (owner and admin hold `tokens.manage`) accepts any `person`, and if it is omitted the token `name` is used, so a token merely named `ada` is Ada. Members are fine: `createMyToken` (`internal/control/session.go:252-270`) forces the caller's own person.
- Scenario: Ada is a member who connected her Linear, Notion or GitHub account. An admin (or a stolen admin session or control token) issues a gateway token `{"name":"x","role":"member","kind":"gateway","person":"ada"}`, connects an AI client and calls `linear__...`. The call runs at Linear as `ada@linear`, with Ada's data and permissions. The audit event names the token (`x`) as actor and records no upstream identity, so the trail does not show whose account was used. ADR 0017 point 6 and acceptance 6 say "never another person's grant"; this is the one path where that is not true. The same applies to approvals and policy: they are evaluated for the token's role, not for Ada.
- How established: RAN, by an existing passing test that does exactly this by design. `test/acceptance/upstream_oauth_test.go:309` (`adaAgent := g.connect(g.issue("ada"))`, where `issue` in `harness_test.go:441-446` posts to `/api/v1/tokens` with the owner token and no `person`) then `:330` shows the call arrive at the upstream as `ada@linear`. The test uses it as a fixture; it is also the exploit.
- Fix: bind the token to the user, not to a string. Store `user_id` on `api_tokens`; `createMyToken` sets it; `POST /api/v1/tokens` with a `person` other than the caller's issues a token that has no user and so gets the "no account" error on oauth servers (service tokens), or is refused for `person` values that name an existing member. Resolve the grant by `user_id`, never by name. Record the upstream account's user id (and the grant's owner) in the call's audit event. Change the acceptance fixtures to issue tokens through the member's own path.

### R-02 Medium: registering again never reaches the running upstream manager, so refreshes use a stale client and can destroy grants

- Where: `internal/web/connect.go:290-299` (the callback calls `Grants.Reregister` and never `Upstream.Sync`); `internal/grants/grants.go:132-154` (`Reregister` updates the stored config and secret); `internal/upstream/perperson.go:130-137` and `internal/upstream/upstream.go` (`catalogTransport`) capture `e.srv`, the snapshot taken at the last `Sync`; `grants.go:267-271` and `:85-120` (`Endpoint` builds the client id from that snapshot and the client secret fresh from the database).
- What is wrong: `Sync` runs only from the admin API (`control.go:347, 404, 422`) and at start. After a re-registration the pool and catalog keep refreshing with the old `ClientID` (and with the new secret read from the database, a mismatched pair). People who connect afterwards get grants issued to the new client, which are then refreshed as the old client. An authorization server answers `invalid_grant` for a refresh token presented by another client, and `doRefresh` (`grants.go:272-279`) answers that by deleting the grant and writing `upstream.grant_lost`. `invalid_client` is only a generic error, so the people whose grants predate the change stay broken until a restart or an admin edit.
- Scenario: the authorization server forgets Privo's dynamic registration (a common trigger on a provider that expires them, or after a provider outage that answers `invalid_client`). The first member to hit it triggers `Reregister` for everyone. From then on every newly connected member loses their grant the first time their access token expires, and older grants cannot refresh. Because any member who can start a connect can reach this branch whenever the token endpoint answers `invalid_client`, the blast radius is the whole org, not one person.
- How established: READ (not run). `TestDynamicRegistrationRetriedWhenRejected` covers only the web response; no test refreshes after a re-registration.
- Fix: call `Upstream.Sync` (or have the manager reload the server by id on every grant use) after `UpdateServerOAuth`; or make `AccessToken`/`RefreshAfterReject` re-read the server's OAuth config from the store instead of taking `e.srv`. Rate-limit and single-flight `Reregister` per server, restrict it to a first `invalid_client` after a recorded success, and audit it as an admin-visible event. Do not delete a grant on `invalid_grant` when the endpoint's client id changed since the grant was issued; store the client id in the grant and refresh with that one.

### R-03 Medium: any member can fill the sign-in state table and lock everyone, owners included, out of sign-in and connecting

- Where: `internal/web/connect.go:224-235` (`connectStart` creates a state per POST), `internal/store/signin.go:386-402` (`CreateOAuthState`: a single org-wide count against `limit`, shared by sign-in, setup, invite and connect states), `internal/web/web.go:43` (`DefaultStateCap = 500`, TTL 10 minutes).
- What is wrong: states are capped per org, not per user, and `connectStart` has no rate limit. A signed-in member (the lowest role that may connect) with the CSRF token of their own session can POST `/connect/<alias>/start` 500 times; each one is a row for 10 minutes. While the table is full, `ErrTooManyStates` ("Too many sign-ins in progress") answers every sign-in, invite claim and connect, including the owner's.
- How established: READ. The cap logic and the lack of any per-user or per-IP limit are visible in the two functions; I did not run the loop.
- Fix: cap connect states per user (a handful) and delete that user's older connect state when a new one starts (each start overwrites the browser's single cookie anyway, so the older rows are unusable); count connect states separately from sign-in states; add a small rate limit on `connectStart`.

### R-04 Low: upstream tokens are deleted locally but not revoked at the authorization server on member removal, server deletion and reconnect

- Where: `internal/store/signin.go:345-360` (`DisableUser` calls `deleteUserGrants`), `internal/store/servers.go:178-200` (`DeleteServer`), `internal/store/upstream_oauth.go:187-192` (`SaveGrant` deletes the previous credential when a person connects again), versus `internal/grants/grants.go:319-338` (`Disconnect`, the only path that calls RFC 7009 revocation).
- What is wrong: only an explicit disconnect revokes. A removed employee's grant, a deleted server's grants, and the old grant replaced by a reconnect (for example after connecting a different upstream account) stay valid at the provider with a long-lived refresh token, for as long as the provider allows. Privo's copy is gone, but copies persist in backups (`store/backup.go`) that are decryptable with the master key. ADR 0017 point 8 words the removal case as "deleted", so the docs are accurate; the gap is that the stronger behaviour is available and the exposure window is real.
- Scenario: a leaver's personal Notion grant is deleted in Privo, the database is restored from last night's backup during an incident, and the leaver's refresh token is valid again at Notion (and usable by whoever holds the restored database and key).
- Fix: have `removeMember` and `deleteServer` call the grant service's revoke for each affected grant before deleting (best effort, as `Disconnect` does), and revoke the replaced grant in the reconnect path. Document backups as holding live grants.

### R-05 Low: an admin-supplied client secret goes to whichever authorization server the MCP server names, unless the admin also pins `issuer`

- Where: `internal/control/upstream_oauth.go:58-60, 78-80`; `internal/upstreamauth/upstreamauth.go:121-127` (`Discover` takes `authorization_servers[0]` when `expectIssuer` is empty); `:540-560` (`token` sends the secret as HTTP Basic or in the form to the discovered `token_endpoint`).
- What is wrong: with `client_id`/`client_secret` supplied, the admin almost always means "my OAuth app at provider X". If `oauth.issuer` is omitted, the issuer comes from the MCP server's own metadata, and the secret is sent on every connect and refresh to the token endpoint that metadata names. A malicious or compromised third-party MCP server at registration time can name its own authorization server and receive the secret (and then each person's code and refresh token for that server, which is by design). The token endpoint need not be on the issuer's origin either.
- How established: READ.
- Fix: require `oauth.issuer` whenever a client secret is supplied; consider requiring the token and revocation endpoints to share the issuer's origin (or registrable domain) unless the admin allows otherwise. Show the discovered authorization server host in the create response and in the admin UI before the first connect.

### R-06 Low: a failed save after a rotated refresh token loses the grant, and concurrent replicas can trigger reuse detection

- Where: `internal/grants/grants.go:286-314` (`doRefresh`): the authorization server has already rotated the refresh token when `UpdateGrantToken` runs; on a database error (`default:` branch) or a context failure the new pair is dropped and the old refresh token is already dead. In the `ErrConflict` branch (another replica won) the loser has also consumed the old refresh token.
- What is wrong: with rotating refresh tokens (acceptance fixture and most providers do this) the next refresh returns `invalid_grant`, `doRefresh` deletes the grant, and the person must reconnect. On Postgres with several replicas two replicas can present the same refresh token within milliseconds; providers with reuse detection revoke the whole family. The code notes the multi-replica case as a known later item (`todo.md` "Later in F07"); the single-node database-error case is not mentioned.
- How established: READ.
- Fix: retry `UpdateGrantToken` (bounded) with the already-obtained token before giving up; log the loss at error level with the server alias; for multiple replicas take a row-level lock (`SELECT ... FOR UPDATE` or an advisory lock) around the whole refresh instead of CAS after the fact.

### R-07 Low: the GitHub sign-in callback consumes any state and sends its PKCE verifier to GitHub before checking the purpose

- Where: `internal/web/signin.go:109-155` (`callbackHandler`: `UseOAuthState` and `GitHub.Exchange(code, callback, st.Verifier)` run, and only then `switch st.Purpose` rejects a connect state), `internal/web/web.go` (one `stateCookie` name shared by sign-in and connect).
- What is wrong: a `PurposeConnect` state holds the PKCE verifier of an upstream flow. Hitting `/auth/github/callback` with that state value and the browser's cookie burns the connect flow and sends that verifier to GitHub's token endpoint. Not exploitable on its own: the attacker must know the state (the authorization server does) and the victim's browser must send the cookie. It does show the purpose check is in the wrong place, and the shared cookie means two concurrent flows in one browser silently kill each other.
- How established: READ.
- Fix: look up the state with the expected purpose (`UseOAuthState(..., purpose)`), and use a separate cookie name per flow.

### R-08 Low: every upstream HTTP request does a database read, a decrypt and a write on the single writer connection

- Where: `internal/upstream/perperson.go:72` (`PersonSession` calls `AccessToken` on every call) and `:316-320` (`bearerRT.RoundTrip` calls it again per HTTP request), `internal/grants/grants.go:197-210` (`usable` reads the grant, opens the ciphertext and calls `TouchGrant`), `internal/store/upstream_oauth.go:340-346` (`TouchGrant` runs an `UPDATE` through `s.w` each time; the `last_used_at <= ?` predicate only avoids changing the row, not taking the write lock).
- What is wrong: one tool call costs two or more writer-lock acquisitions plus reads and AES-GCM opens. The writer is the same connection that audit intents and completions need (the audit write is on the critical path of every call), so heavy per-person traffic slows audit and, with it, every tenant call.
- How established: READ.
- Fix: cache the opened token in memory until its expiry minus skew (keyed by grant id and row version, dropped on disconnect and on `ClosePerson`), and do the touch in memory with a periodic flush.

### R-09 Info: observations, none blocking

1. `insufficient_scope` ends in the gateway's generic "did not answer or failed" message (known, `todo.md` F07 task list). A 401 that carries `insufficient_scope` is passed through unchanged by `bearerRT` (`perperson.go:327`); 403 is not looked at. Fail closed, but the person gets no way forward until step-up lands.
2. A server that rejects every token (wrong audience because the authorization server ignores `resource`, a suspended account) makes each call run one refresh and rotate the refresh token (`perperson.go:330-336`, `grants.go:215-217`). There is no backoff and no cap.
3. Per-person definitions are not pinned: tools are listed and pinned from the catalog grant (an admin's account), but a call executes on the caller's account, whose tool definition for that name can differ (dynamic or per-account tools). ADR 0017 point 6 accepts this; it is worth stating in the F07 residual risks.
4. The tools an admin's account exposes are visible to every member; the todo lists it as a residual risk.
5. `Discover` makes up to about eight sequential requests with a 10 s timeout each inside one admin HTTP request (`upstreamauth.go:102-140`, `:337`), so an admin request can take over a minute against a slow server.
6. Dynamic registration happens before `CreateServer` (`control.go:324`); if the create then fails (alias conflict) the registration at the authorization server is orphaned. Registration responses are not checked for the registered `redirect_uris` (`upstreamauth.go:416-431`).
7. The PKCE verifier is stored as plaintext in `oauth_states.verifier` (10 minute lifetime). Useless without the code, but it is the one secret in that table not hashed or sealed.
8. Returned `scope` is stored but never compared with the requested scopes (`upstreamauth.go:593`), so a broader grant than requested is silently kept.
9. Discovered metadata is stored once (`DiscoveredAt`) and never re-validated; a CIMD client id is derived from `PublicURL` at use time, so changing the public URL changes the client id of every existing grant.
10. Narrow race: `ClosePerson` run while `connectPerson` is mid-handshake (`perperson.go:102-114`) inserts a session established with the old token after the close. Each later call re-checks the grant, so only an upstream that binds an MCP session to the first token and ignores later bearers could be affected.

## Checked and found sound

- **SSRF and metadata fetching.** Every discovery, registration, token and revocation request goes through the egress client (`serve.go:131`), whose dialer checks the resolved IP at connect time (defeats rebinding; loopback, private, link-local, metadata and NAT64/6to4/Teredo ranges refused unless an operator allow-lists them). `do` (`upstreamauth.go:783-818`) disables redirects, reads at most 256 KiB, bounds the whole request (headers and body) at 10 s, and `transportError` removes the URL from errors. `resource_metadata` from a 401 must be on the server's own host (`:262`). Errors never repeat upstream text (only a validated `[a-z_]{1,40}` error code). The only residual SSRF reach is to hosts inside an operator-allowed CIDR, where an authorization-server URL can be pointed at them; that is an operator choice (ADR 0008).
- **Issuer and resource checks.** The issuer in the metadata must equal the string it was looked up for (`:314`), RFC 8414 is tried before OIDC, `authorization_servers` must contain an admin-pinned issuer, S256 is mandatory, every endpoint must be https (http only on loopback), and the resource identifier must cover the server URL on the same origin (`resourceCovers`, with port and case normalisation). Mix-up at connect time is closed twice: the state is bound to the server and issuer, the token endpoint is read from the stored server, never from the callback, and `iss` is refused when present and different or when promised and missing (`connect.go:272-277`).
- **PKCE, state, binding.** Verifier 256 bits from `crypto/rand`, S256; state and cookie nonce 256 bits each; the stored key is `HashSecret(state, nonce)`, so a callback from a browser without the cookie finds nothing and does not burn the real state; `UseOAuthState` is a single `DELETE ... RETURNING` with expiry (single use, atomic); the callback requires the same session id and user id as the start (`connect.go:261`) and the state's purpose; `connectStart` needs the CSRF form token and same origin. Login CSRF in either direction (attacker's code into the victim's account, or the reverse) therefore fails at the cookie nonce, the session check and the CSRF token. The connect link handed to AI clients is a fixed `PublicURL/connect/<alias>` page that needs a signed-in session; it carries no secret, grants nothing by itself and cannot be pointed at another URL (alias is regex-checked and path-escaped).
- **Tenancy in the store.** Every grant, credential, invite and state query in `upstream_oauth.go` and `signin.go` carries `org_id`; methods take a typed `OrgID`; `SaveGrant` verifies server and user belong to the org and the user is not disabled; `UpdateGrantToken` re-checks the credential id (reconnected meanwhile) and CAS on `row_version`; `DeleteServer` removes credentials, grants and pins in one transaction.
- **Vault binding.** AAD length-prefixes org, credential id, owner, server, purpose, key and row version. `store.Grant` rebuilds the credential's owner and server from the grant row, not from the credentials row (`scanGrant`), so swapping `credential_id` between grants, users or servers fails to open. A refreshed token is resealed with the next row version, so an older ciphertext cannot be replayed. The upstream manager's static-secret loader skips grant and client-secret credentials (`upstream.go:657`).
- **Secrets handling.** `Token` prints as redacted for every `fmt` verb; no log line in `grants`, `upstreamauth`, `connect.go` or `perperson.go` takes a token, code or verifier; `connectionView` and the server view carry no token or secret; client secrets are write-only and sealed. Tokens are added by a transport inside the origin lock (order verified in `httpTransport`/`originLocked`: origin check first, then bearer, then egress), so a redirect or SSE `endpoint` event cannot carry the bearer to another origin; hooks never see the Authorization header.
- **Refresh.** Single-flight per `(org, server, user)`; runs on a context detached from the caller with its own 20 s deadline so a cancelled caller cannot leave a rotated token unsaved (`TestRefreshSurvivesCallerCancel`); the second caller re-reads and uses the newer token when the stale one differs; `invalid_grant` deletes the grant with an audit event; `resource` is sent on authorize, exchange and refresh (RFC 8707); an unrotated refresh token is kept.
- **Per-person isolation in `perperson.go`.** Pool key is `(serverID, userID)`; the token source closes over the user id and org of that key; the grant is checked before reusing a pooled session on every call, so a disconnected or removed person stops at once; `ClosePerson`, `CloseUser` and `Sync` close sessions; the catalog is a separate supervised session; sessions carry a panic-recovering receive middleware; concurrent first calls share one connection. No code path falls back to another person's or the catalog grant (`gateway.session`).
- **Member removal.** `DisableUser` deletes sessions and grants in one transaction, the gateway re-checks `DisabledAt`, `removeMember` revokes tokens that carry the person and closes pooled sessions, and `CreateInvite` refuses a name that exists, including a removed member's, so a person name cannot be reused to inherit anything.

## Limits

- R-02, R-03, R-04, R-05, R-06, R-07 and R-08 are argued from the code and were not executed. R-01 is demonstrated by an existing passing acceptance test, which I read and ran as part of the package suite only through the packages listed above; I did not run `test/acceptance` itself.
- I did not exercise a real provider; behaviour of authorization servers on `resource`, refresh-token reuse and `invalid_client` is stated from the RFCs and common practice.
- Invites, GitHub sign-in and the Preact app are covered by their own reviews and were looked at only where they touch the connect flow.
